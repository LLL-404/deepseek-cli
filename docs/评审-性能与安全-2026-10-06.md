# 评审：性能与安全隐患（dskts / dsk.py）

- 日期：2026-10-06
- 范围：`dskts/src/*.ts`（现行版）、`dskts/bin/*`、`dskts/tools/*`、`dsk.py`（Python 后备版）
- 方法：全量代码走读 + 定点实验 4 组（含 **3 条崩溃向量实弹复现**、1 组耗时实测，方法见附录）
- 结论：**S1、S2 建议尽快处理**；其余 4 条安全项、4 条性能项为低危加固；无结构性问题

## 一、安全

### S1 [中] 帧协议无校验：5 字节即可打死 keeper（3 条向量已实弹复现）

位置：

| 点 | 位置 |
|---|---|
| `JSON.parse` 裸调用 | `src/frame.ts:29` |
| 帧体不做形状校验，直接取 `frame.op` | `src/keeper.ts:217` |
| `handlers` 是普通对象字面量（原型链穿透 `if (!handler)`） | `src/keeper.ts:195,217` |
| `handler(...).then` 未防御 | `src/keeper.ts:227` |

| 向量 | 载荷 | 结局 | keeper 日志证据 |
|---|---|---|---|
| 非法 JSON | `len=9` + `not json!` | exit 1 | `[dying] uncaughtException SyntaxError ... at JSON.parse (frame.ts:29)` |
| JSON 合法但非对象 | `len=4` + `null` | exit 1 | `[dying] uncaughtException TypeError: Cannot read properties of null (reading 'op') (keeper.ts:217)` |
| 原型链 op | `{"op":"constructor"}` | exit 1 | `[dying] uncaughtException TypeError: handler(...).then is not a function (keeper.ts:227)` |
| 对照：连上即断（CLI 探活用法） | 无数据 | **存活**（正常） | — |

触发面：本机任意进程（含其它 Windows 账户——TCP 回环无用户隔离）。
影响：keeper 自杀 + 进行中的提问被打断（问题已提交、答案丢弃）+ 下一次命令付冷启动（≤15s）。无持久损害、可自愈。

修法（约 30 行，一次改完三条向量）：

1. `frame.ts` `push()` 里 try/catch `JSON.parse`，解析失败按坏帧处理（不抛出到事件循环）。
2. `keeper.ts` 解码回调开头做形状校验：`obj` 必须是对象且 `typeof obj.op === "string"`。
3. `handlers` 改用 `Object.create(null)`，或命中判定改 `Object.hasOwn(handlers, frame.op)`——普通对象字面量会从原型链取到 `constructor`/`toString` 这些真函数，绕过 `if (!handler)`。
4. 坏帧处置：回一帧 `{ok:false, error:"bad frame", code:1}` 后 `socket.destroy()`；进程不退出。
5. 客户端 `frame.ts:56-64`（rpc）同步加固，对称处理。

### S2 [中｜对既有取舍的加固] 3928 无鉴权：暴露面比「问答」大

位置：`src/keeper.ts:250`（`listen(3928, "127.0.0.1")`）、`src/constants.ts:34`（注释自认取舍）。

任何能连上 3928 的本地进程可执行：

| 能力 | 调用 | 后果 |
|---|---|---|
| 上传本地文件到 DeepSeek 账号 | `ask` + `files` | 数据外泄原语（受页面 `input[accept]` 白名单限制；该白名单实际内容未核实，见 `pageops.ts:255-264`） |
| 在任意会话里提问 | `ask` + `chat`（**无归属限制**，只按标题子串找） | 模型能看到该会话上下文，回答可转述私人对话内容 |
| 列全部会话标题 | `chats` | 会话清单泄露 |
| 删任意会话（单条命中） | `rm` + `any` + `yes` | 破坏性 |
| 删登录态 | `down` | 破坏性 |

R8 的「单人单机」假设需补一条：**回环端口对同机其它账户同样开放**。两级加固：

- A（小）：keeper 启动生成随机 token，写 `%LOCALAPPDATA%\dsk-ffprofile.token`（用户私有 ACL）；CLI 每帧带上，keeper 校验不符即断。边界从「全机」收到「本用户」。
- B（彻底）：改 Windows 命名管道 `\\.\pipe\dskts-keeper`（默认 ACL 仅本用户 + 管理员，落地前实测确认）。代价：CLI 连接串改一行；旧 keeper 与旧 CLI 一次性不兼容。

### S3 [低] 帧长无上限

位置：`src/frame.ts:25`（`readUInt32BE` 最大 4GB）。
现状：未预分配，内存只随实发字节增长（要真发够字节才能撑爆）——本地进程可做内存型 DoS。
修法：加 `maxLen`（如 64MB），超限按坏帧断开。

### S4 [低] 残留清扫（sweep）匹配面双向偏差

位置：`src/sweep.ps1:5-6`（`node.exe` + `*keeper.ts*`；`firefox.exe` + `*dsk-ffprofile*`）。

| 方向 | 事实 | 后果 |
|---|---|---|
| 误杀 | `*keeper.ts*` 是子串匹配 | 其它项目里恰好叫 `keeper.ts` 的常驻 node 会被清掉 |
| 漏杀 | explorer 代启的 keeper 命令行是 `keeper-boot.mjs`，**不含 `keeper.ts`** | 「活着但卡死」的代启 keeper 清不掉；`down` 也走不到兜底（连得上就不走 fallback），只能手工关窗口/thunderkill |

修法：给 keeper 一个可判定标记（`keeper-start.cmd` 与常规 spawn 都追加 `--dsk-keeper`），sweep 匹配 `'*--dsk-keeper*'` 且限定 `node.exe`。

### S5 [低] dsk.py 数 cookie 时把整库明文拷进 %TEMP%

位置：`dsk.py:89-105`（`tempfile.mkstemp` + `shutil.copyfile`）。
过程：为统计条数，把主 profile 的 `cookies.sqlite`（全部站点 cookie，明文）完整复制到 `%TEMP%`；正常路径 `finally` 删除，进程被强杀会残留。
修法：SQLite 只读 URI 直开原库（`file:...?immutable=1`）；或临时名加固定前缀 + 启动时清扫。

### S6 [低] explorer 引导 .cmd 未转义 `%`

位置：`src/env.ts:131-141`。
场景：`%LOCALAPPDATA%` 或 node 路径含 `%`（用户名里带 `%`）→ cmd 展开变量 → 启动失败或语义不对。
修法：写入 `.cmd` 时 `%` → `%%`（一行）。

## 二、性能

### P1 [低-中] 每次提问两次整页导航

`cmdAsk` 先 `checkLogin`（`keeper.ts:107-112`：goto + 固定 2s）→ `askFlow` 再 `gotoChat`（`askflow.ts:36`）。每次多付一次整页加载（视网络约 1~4s）。
修法：二选一——checkLogin 降级为「读当前页是否登录」（不导航）；或 askFlow 判断已在 chat 首页则跳过 `gotoChat`。

### P2 [低] 冷启动清扫：PowerShell 728ms，且 spawnSync 无 timeout

实测（本机）：空 PowerShell 启动 334ms；`sweep.ps1` 实跑 **728ms**；tasklist 对照 235ms。相对 ≤15s 冷启动可接受，但 `spawnSync`（`env.ts:72-75`）**没设 timeout**——PowerShell 若卡住，CLI 一起无限卡。
修法：`timeout: 20_000`；想再省可换 tasklist 实现。

### P3 [低] renameTo 对全页每个 input 逐个探测

`pageops.ts:312-321`：每个 input 两次 CDP 往返（isVisible + inputValue），页面 input 多时几十次往返。
修法：范围收窄到弹窗容器（如 `[role=dialog] input`）；命中即 break 的逻辑已有。

### P4 [低] keeper 日志无轮转/上限

`keeper.ts:23-28` 只追加。当前 43KB；长期无界。
修法：keeper 启动时 >10MB 归档/截断。

### P5 [说明] 读数成本与时限语义

每拍 3s 一次 `innerText` 全文读取（长答案几十 ms 级）——可接受，不必动。`judge.waitedMs` 是「计划时间」（拍数×tick），真实用时略大；外层 rpc 超时（max-wait+180s）兜底，无风险。

## 三、顺手发现（不在性能/安全主题内）

| # | 位置 | 事实 | 建议 |
|---|---|---|---|
| A1 | `bin/dskpy.cmd:2` | 无回落链（sh 版有：`$DSK_PY` → 仓库根 → `~/.qoder-cn`）；仓库内直接运行找不到 dsk.py，只有部署目录布局可用 | 与 sh 版对齐，或注释写明「仅部署目录」 |
| A2 | `env.ts:105-149` | explorer 代启「假成功」（spawn 不抛但 explorer 没起）后无直接兜底，干等 20s 报超时 | 代启后 N 秒端口没起，再补一次常规 spawn |
| A3 | `dskts.ts:88-99,208` | `--max-wait` 无上限；约 ≥214 万秒触发 Node setTimeout 32 位溢出（本地已验证：1ms 即超时，keeper 后台照跑答案丢弃） | clamp（如 ≤3600） |
| A4 | `tools/gate.ts`、`tools/probe_prime.ts` | 直接用与 keeper 同一 profile 目录；keeper 在跑时重跑会撞（Firefox profile 锁） | 运行前检 keeper 是否在跑，或换独立 profile |

## 四、已核无问题（正向清单）

| 项 | 结论 |
|---|---|
| JS 注入面 | 无。页面交互全部 Playwright `fill`/`press`/`setInputFiles` 传值；dsk.py 的 JS 全走 `arguments`。无字符串拼接进 `evaluate` |

| 依赖面 | 运行时依赖仅 `playwright` 一个，有 lock；无构建产物 |
| 凭据面 | 只存在 profile 目录（dskts）/ 副本目录（dsk.py）；`down` 整体删 |
| rm 防护 | 前缀白名单 + 默认演练 + 单条命中 + `--any` 越界（`pageops.ts:360-388`） |
