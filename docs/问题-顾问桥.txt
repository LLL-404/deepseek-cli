前提（照此作答，别按通用云服务的假设）：单人本地工具；零第三方框架；执行器是一台 Windows 机器上的弱模型，只会机械执行；网页端这个模型**看不到执行器的机器**，只能读我发给它的文字；本地没有任何常驻模型运行时。

分工刚刚改成这样：你（网页模型）当总架构师——质疑目标、侦察环境、定阶段、做根因分析、动态重规划、需要时自己写脚本；本地弱模型当机械手，**只读你回复里两个机器块**（一个 STATE 块存状态、一个 EXEC 块给多步指令），其余分析文字一律不读；两个块之外你可以随便想、随便写。STATE 每轮由你重写、本地整块覆盖，作为跨轮记忆。

一、一次 EXEC 给 5–8 步，本地有两种跑法：跑完整批再回简报，或者每跑完一步就回问一次。除了「一步一停」和「全跑完」这两个极端，还有哪些分段策略？请按「弱模型执行器」这个前提评每条：什么情况下批量跑会更稳（例如步骤之间互相依赖、中间态无法压缩进简报），什么情况下会更快失控（例如第一步就把工作目录改了，后面几步全部基于错假设）。失败时该由谁决定回滚——你在 STATE 里预先写回滚步，还是本地停下后再问你？

二、EXPECT 要给弱模型机械判定。我打算只认五种形式：`exit=N`、`包含:X`、`不含:X`、`regex:X`、`非空`，其余一律判「未判定」（rc=0 就继续，但不算满足）。请指出我漏掉的常见坑：哪些预期表达方式在实践中最容易被弱模型误判；「未判定」继续跑到底比「未判定」就停更危险还是更安全；以及如何防止你写出的 EXPECT 本身就和 CMD 的实际输出格式不一致（例如你期望 `包含:Python 3` 但命令输出 `Python 3.12.7` 之外的另一种排序）。

三、简报有硬性字数上限（我这边 6000 字，超了就报错不截断）。STATE 会越写越长。两种做法：每轮把 STATE 全量重发（简单但挤占预算），只发与上一轮的差异（省预算但依赖本地保存的旧状态，一旦漂移就再也回不来）。请按「上下文不互通、只能靠文件滚动记忆」这个前提评：差异式记忆在什么条件下必然崩坏；有没有第三种压缩法（例如按字段分优先级、把已完成项折叠成计数、只保留最近 N 条决策）能同时避开「上下文丢失」和「静默漂移」，各自的判定成本是多少。

四、危险闸门：你自己会在每一步标 `DANGER: no|yes`，本地另有一套按关键词扫命令字符串的扫描（删除/覆盖/支付/对外发送/装软件/改系统设置/杀进程/丢弃工作区）。我打算取并集：标 yes 或者扫描命中，都停下来交给人，且没有任何参数能降级这条。除并集外还有什么组合方式？两种不一致的情况分别怎么处理才既安全又不把工具废掉：(a) 你标 yes 但那条命令其实无害；(b) 你标 no 但扫描命中。另外，关键词扫描必然能被改写法绕过（把删除写成别的调用形式），在「命令必须是单行字符串交给 shell」这个约束下，有什么结构上更硬的做法？
