# 07 · 设计决策记录

> 一句话摘要：关键技术选型背后的背景、理由、代价，以及各自何时值得重新考虑。

每条决策记录包含五段：**决策 / 背景 / 理由 / 代价 / 触发重开条件**。这里只记「为什么长这样」，具体行为见对应章节。

## D1 用 Playwright 驱动持久 profile

- **决策**：用 Playwright 驱动一个**有头的 Firefox 持久 profile**，而不是官方 API、内置浏览器或桌面自动化。
- **背景**：目标是不开 API 付费、不新建账号、不撞图形人机验证地拿到完整答案。可选路线里，官方 API 需要 key 与另外充值；桌面自动化要求先识别出浏览器地址栏 URL，而火狐标题栏不携带 URL，实测会中断整轮。
- **理由**：复用已有登录态；不触发人机验证；不与用户正在使用的浏览器窗口冲突；Playwright 提供了可靠的可视性等待与输入能力。
- **代价**：引入 `playwright` 依赖与浏览器二进制；取词仍依赖页面的 DOM 类名，改版即失效；自动化的是已登录的网页界面，未必符合站点服务条款，风险由使用者承担。
- **触发重开条件**：官方 API 变得可用且成本可接受；或站点提供了机器可读的正当接入方式。

## D2 引入常驻 keeper

- **决策**：在 CLI 之外引入一个**常驻进程**持有浏览器上下文，CLI 通过私有帧调用它。
- **背景**：**Playwright 的 Firefox 不支持二次连接已经启动的浏览器**——进程一退，下次就只能重新启动浏览器。
- **理由**：把冷启动成本从「每次问答」变成「一次性」。keeper 已在时走热连接，连接与页面就绪约 3 秒（不含模型生成本身）。
- **代价**：多一个需要管理的进程（启动、停止、残留清扫、锁）；一次只能服务一条命令；在会清理进程树的宿主里还要额外绕路（见 D5）。
- **触发重开条件**：Playwright 支持 Firefox 重连；或换用别的浏览器与驱动组合。

## D3 完成判定用双信号

- **决策**：**文本连续多拍不变** 且 **「停止」按钮消失**，两者同时成立才算答完。
- **背景**：生成过程中会出现停顿。若只看文本是否稳定，一遇停顿就会把半截答案当成品返回，而且**退出码仍是 0**——调用方无从察觉。
- **理由**：两个信号互相独立：文本稳定性反映内容是否还在增长，停止按钮反映页面自认的生成状态。任一单独都不足信。
- **代价**：判定偏保守，很快出完的答案也要等过最短等待时间与稳定拍数；取消或异常结束时依赖上限收摊。
- **触发重开条件**：能直接拿到页面的响应流与明确的结束标志——那正是已搁置的扩展路线要解决的。

## D4 归属识别放在 CLI 侧

- **决策**：在**每次调用产生的 CLI 进程**里判断「这次是哪个 Agent」，把结果（mark）随帧传给 keeper。
- **背景**：keeper 是常驻进程，它的进程环境属于**第一个把它拉起来的那个 Agent**，之后不会改变。若在 keeper 侧读环境变量做识别，第二个 Agent 连上来读到的还是老环境，必然认错。
- **理由**：只有每次新起的 CLI 进程，其环境才真实反映本次调用方。
- **代价**：帧里多带一个字段；keeper 要信任 CLI 传来的 mark（同用户进程之间本就互信）。
- **触发重开条件**：keeper 能按连接区分调用方环境——当前模型不支持。

## D5 请 explorer 代启 keeper

- **决策**：Windows 上优先请 `explorer.exe` 代为启动 keeper（等价于「双击一个 .cmd」）；不可用时退回常规 spawn。
- **背景**：某些宿主（IDE 沙箱、命令执行器、CI runner）会在**命令结束时按快照清理该命令产生的所有进程**——包括孙进程。实测中 `detached: true` 与「托孤」都挡不住，keeper 与浏览器会一起消失，而 keeper 日志里一行痕迹都没有（说明不是自己退的）。
- **理由**：explorer 启动的进程**不属于任何命令的进程树**，宿主扫不到它，能真正常驻。实测同法启动的进程可跨命令存活。
- **代价**：首次会弹出一个控制台窗口（它同时是 keeper 的日志窗与「关掉即停」的开关）；要求 node 路径与引导目录为纯 ASCII，否则自动退回 spawn。可用环境变量禁用这条路线。
- **触发重开条件**：宿主不再做快照式进程清理；或工具形态改为长期安装的服务。

## D6 手写私有帧协议

- **决策**：自己实现「4 字节大端长度 + JSON」的私有帧，不引入 RPC 框架。
- **背景**：协议只在回环上自用，通信双方只有自家两个进程，命令面只有十来个。
- **理由**：握手与分帧总共几十行，比多养一条依赖链更看得懂、也更容易在出问题时替换。
- **代价**：坏帧防护、长度上限、原型链污染这些安全细节都要自己兜——事实上补过一轮实弹加固（见 [05-协议与接口契约](./05-协议与接口契约.md)）。
- **触发重开条件**：需要跨机通信，或协议面显著变大。

## D7 帧带会话 token

- **决策**：keeper 每次启动生成随机 token 写入用户私有目录，CLI 每帧携带并接受校验。
- **背景**：监听端口是回环 TCP，**对同机所有账户开放**；而 profile 与 token 文件所在的目录受用户 ACL 保护。
- **理由**：借文件系统 ACL 把访问边界从「全机所有账户」收到「本用户」。它不防同用户进程（同用户本就能读该文件），只防其他账户。
- **代价**：多一个文件与一次校验；token 读不到时要给出可诊断的提示而不是静默失败。
- **触发重开条件**：改用仅本用户可访问的进程间通道（如命名管道），届时 token 机制可以退休。

## D8 删除默认只演练 + 前缀白名单

- **决策**：`rm` 默认只演练（走到确认框点「取消」）；只删标题带已知 Agent 前缀的会话，跨出白名单必须显式加参数。
- **背景**：早期版本用**正文关键词**判断会话归属，结果**误删了作者自己的两条会话**。
- **理由**：删除不可逆，宁可多一步确认。归属只认显式的前缀，不猜测。
- **代价**：自动化删除要先加 `--yes`；删除无前缀的会话要显式越权。这是刻意的摩擦，不是缺陷。
- **触发重开条件**：无——这条安全摩擦有意长期保留。
