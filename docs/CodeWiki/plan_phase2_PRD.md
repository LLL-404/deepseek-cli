## 一、产品概述与背景

**背景**：`dskts` 已完成从 Python/Marionette 版的迁移，旧实现与它的设计件（`DESIGN.md`、`DESIGN-dsk2.md`）已于 2026-10-07 移除。眼下项目知识散落在四处：`dskts/README.md`（用法与设计散文）、`output/`（迁移规划与 Gate 验收）、`docs/`（外部评审原文）、以及源码注释里的实测教训。没有一份**面向新读者的结构化入口**。

**产品定位**：一套只读的 Code Wiki，作为 `dskts` 的知识入口。**它是索引与骨架，不是源码的替代品**——读者据此知道「去哪看什么」，而不是在这里读完所有细节。

**非目标**：
- 不写使用教程、不写新手指引式 step-by-step。
- 不替代源码注释（注释解释局部 why，Wiki 解释整体结构与边界）。
- 不改动任何源码。

## 二、读者故事

| 读者 | 故事 | 验收信号 |
|---|---|---|
| 新接手者 | As a 新接手者, I want 按索引给出的顺序读完「概览 → 架构」两章就能说清这个项目为什么必须有两个进程, So that 我不必通读全部源码即可建立正确心智模型。 | 能口头答出「Firefox 不支持二次连接」这一根因 |
| 其他 Agent | As a 调用方 Agent, I want 一份命令表 + 退出码语义 + 三流契约, So that 我能用管道正确调用并按退出码分流处理。 | 能仅凭文档写出一次带 `--out` 的调用并判断失败类型 |
| 评审者 | As a 评审者, I want 每个模块的「只该知道 / 不该知道」与「改它牵动谁」, So that 我能判断一次改动的影响面。 | 能对任一 `src/*.ts` 说出上下游 |
| 维护者 | As a 维护者, I want 选择器、协议、常量的唯一登记处索引, So that 页面改版或协议变更时我知道该动哪几个文件。 | 能指出四个选择器的唯一定义位置 |

## 四、非功能需求

**准确性（最高优先）**
- 每条结论必须能落到具体文件或行为依据；找不到依据的不写。
- 未实测的事实必须显式标注「未实测」（沿用项目既有习惯）。
- 描述与源码矛盾视同缺陷，验收一票否决。

**不腐化**
- 不整段复制源码；关键处给短片段 + 文件链接，避免文档与代码双份维护。
- 常量、选择器、退出码只指向唯一定义处（`constants.ts`），不在文档里复述数值，避免两处不同步。
- 章节之间不重复：同一事实只写一处，其余处引用。

**可定位性**
- 小节标题与正文使用真实标识符（`createJudge`、`fillAndVerify`、`KEEPER_PORT`），便于全文搜索直接命中。
- 所有文件引用使用可点击链接，目标必须存在。

**可读性**
- 中文表述；每章首行一句话摘要；术语统一（keeper、CLI、归属标记、连续会话、帧）。
- 面向「没读过源码的人」，不预设读者了解 Playwright 或 Firefox 自动化。

**边界**
- 不引用已删除的产物（`dsk.py`、`DESIGN.md`、`DESIGN-dsk2.md`、`dskpy`）作为现行事实；涉及历史沿革时明确标注为「已移除」。
- `output/`、`docs/` 内容是历史存档，引用时必须标明其历史性质。

## 五、验收标准

1. Phase 1 清单中的 5 项 P0 全部覆盖，4 项 P1 全覆盖，P2 尽力覆盖。
2. **速读测试**：只读索引 + 概览 + 架构，能答出「为什么必须有两个进程」与「一次提问经过哪些步骤」。
3. **可定位测试**：文档中出现的每个文件名、函数名、常量名，均能在仓库中精确定位；所有链接可点且目标存在。
4. **一致性抽查**：随机抽 5 处文档陈述与源码比对，全部一致。
5. **无悬空引用**：`grep` 文档集，不出现指向已删除产物的现行性引用。
6. 每章均含「一句话摘要」与「依据」小节，骨架统一。
