# Code Wiki 技术规格（dskts）

> 阶段产物 · Phase 3 / 4
> 上游：[plan_phase2_PRD.md](./plan_phase2_PRD.md)

## 一、技术选型与理由

| 决策 | 选择 | 理由 |
|---|---|---|
| 载体格式 | 纯 Markdown，无静态站点生成器 | 读者是开发者与 AI Agent，Markdown 在编辑器、终端、GitHub、Agent 检索下都可读；引入 mkdocs/docusaurus 会加一条构建链，收益不成比例。 |
| 文件组织 | 索引 + 9 个章节文件 | 单文件会超长、不利定点维护；多文件按章节拆分，改动只碰对应文件。 |
| 链接方式 | 站内相对路径 + 源码绝对链接（`file:///…#L12-L34`） | 相对路径随仓库迁移不失效；源码链接直接跳转。 |
| 行号策略 | **以「文件 + 符号名」为主定位，行号为辅** | 行号会随代码改动漂移；只写行号会在下次改动后全部失真，符号名则长期有效。 |
| 数值策略 | **不复述常量数值**，只指向 `constants.ts` | 端口、超时、选择器这类值有两处就一定会不同步。 |
| 代码片段 | 只贴短片段（≤15 行），且以解释结构为目的 | 整段复制等于把文档变成第二份源码，必然腐化。 |
| 图 | 文字描述 + 表格；不引 Mermaid 之外的工具，Mermaid 可选 | 文字/表格在任何渲染器下都不丢信息；Mermaid 作为增强而非必需。 |

## 二、信息架构（阅读路径）

```
README.md（索引）
   │
   ├─ 速读路径：01-概览 → 02-架构与时序 → 06-运行方式
   ├─ 全量路径：01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09
   └─ 按需路径（索引里的「我想知道 X → 看第 N 章」表）
```

**依赖方向**：01 独立；02 依赖 01 的定位；03 是 02 的展开；04 是 03 的深化；05/06 可脱离前四章单独读；07/08/09 是横切主题，可与任意章并行读。

**每章固定骨架**：
```
# 标题
> 一句话摘要
（正文：表格 / 分点 / 短片段）
## 依据
- 结论 → 文件 + 符号名（+ 行号）
```

## 三、写作规范

**术语统一**（首次出现给定义，之后固定用词）：

| 术语 | 含义 |
|---|---|
| keeper | 常驻进程，持有 Playwright 浏览器上下文 |
| CLI | 每次调用产生的命令行进程 |
| 归属标记（mark） | 会话标题前缀，形如 `WorkBuddy｜` |
| 连续会话 | 每个 Agent 的默认会话 `<Agent 名>｜连续会话` |
| 帧（frame） | CLI 与 keeper 之间的私有消息单元 |
| 一拍（tick） | 判定循环的一次采样间隔 |
| 读数（reading / sample） | 一拍从页面取到的 `{text, busy, count}` |
| 双信号 | 判定完成的两个条件：文本稳 N 拍 **且** 停止按钮消失 |

**硬性规范**：
1. 每章首行是一句话摘要，不写第二句。
2. 小节标题用真实标识符（`createJudge`、`ownerOf`），便于全文搜索命中。
3. 结论必须可追溯：正文里出现的每个事实，在「依据」小节有对应条目。
4. 未实测的事实显式标注「未实测」。
5. 不出现指向已删除产物（`dsk.py`、`DESIGN.md`、`DESIGN-dsk2.md`、`dskpy`）的现行性陈述；提及历史时加「已移除」。
6. 引用 `output/`、`docs/` 内容时，必须标明「历史存档」。
7. 同一事实只写一处，其余处用相对链接引用。
8. 中文表述；不预设读者懂 Playwright。

## 四、各章详细大纲

### README.md（索引）
- 一句话摘要
- 这是什么（三行以内）
- 阅读路径：速读 / 全量 / 按需
- 「我想知道 X → 看哪一章」对照表
- 章节一览（文件 / 摘要 / 优先级）
- 本 Wiki 的阅读约定（术语表位置、链接约定、「未实测」标注约定）

### 01-概览与演进.md
- 一句话摘要
- **它是什么**：终端里问 DeepSeek 网页版，答案到 stdout、过程日志到 stderr
- **要解决的问题**：不开 API 付费、不建新账号、不撞图形人机验证
- **成功判据**（五条，来自项目自身定义）
- **明确不做**：不伪造反爬令牌、不在浏览器外重放凭据、不做多站点抽象等
- **演进沿革**：原 Python/Marionette 版已移除，现有唯一实现；`dsk` 命令名的移交状态
- 依据

### 02-架构与时序.md
- 一句话摘要
- **双进程模型**：CLI ↔ keeper ↔ 浏览器（文字图 + 端口/协议的关系）
- **为什么必须两个进程**：根因是 Playwright 的 Firefox 不支持二次连接已启动的浏览器
- **一次提问的完整时序**：从 `dskts "问题"` 到答案落 stdout 的分步走查（含 checkLogin、选会话、开关、附件、填题回读、前提校验、提交验证、判定循环、改名）
- **三流契约**：stdout / stderr / 退出码各自承载什么
- **磁盘状态布局**：`dsk-ffprofile`、`.lock`、`.token`、`.log`、`dsk-keeper-boot`，谁建谁删
- 依据

### 03-模块职责与依赖.md
- 一句话摘要
- **分层总表**：常量层 / 协议层 / 环境层 / 客户端 / 判定层 / 页面层 / 编排层 / 进程层 / 入口
- **逐文件卡片**（`src/` 十个文件，每张卡片五个字段）：职责 / 只该知道 / 不该知道 / 依赖谁 / 谁依赖它 · 改它牵动谁
- **模块依赖图**（文字或 Mermaid）
- **外部依赖**：运行时仅 `playwright`；devDependencies 为 `typescript` 与 `@types/node`
- 依据

### 04-关键函数与类型.md
- 一句话摘要
- 按模块分组的符号表（签名 / 职责 / 关键行为 / 调用方）：
  - keeper 生命周期：`ensureContext`、`opUp`、`opAsk`、`opDown`、`server` 回调与 `handlers` 表
  - 编排：`askFlow`
  - 页面层：`readOnce`、`convAnchorsWait`、`selectSession`、`setToggles`、`fillAndVerify`、`guardNotBusy`、`submitWithVerify`、`attachFile`、`renameTo`、`rmConversation`、`judgeLoop`、`makeJudge`
  - 判定：`createJudge`（状态机与终态：`done`/`truncated`/`noRender`）
  - 身份：`resolveMark`、`detectAgent`、`ownerOf`、`homeTitleFor`、`normalizeName`
  - 协议：`encodeFrame`、`createFrameDecoder`、`rpc`
  - 环境：`ensureKeeper`、`launchKeeperViaExplorer`、`sweepStale`、`downFallback`
- **核心类型**：`Sample`、`Reading`、`Judge`/`JudgeConfig`/`TickVerdict`、`Frame`/`FrameResp`、`AskParams`/`AskResult`、`FlowError`、`ProbeReport`
- 依据

### 05-协议与接口契约.md
- 一句话摘要
- **帧格式**：4 字节大端长度前缀 + JSON（短示意）
- **帧体上限与坏帧处置**：超限/非法 JSON 只断连接、不杀进程
- **token 门卫**：生成、存放位置、校验时机、不符的处置
- **命令表**：`ping` / `status` / `up` / `checkLogin` / `ask` / `chats` / `rm` / `probe` / `diag` / `down`，各自的参数与返回
- **进度帧**：`progress: true` 与 `--stream` 的配合
- **退出码契约**：0 / 1 / 2 的语义与 `FlowError.code` 的映射
- **并发语义**：命令串行、忙时退 2 不排队
- 依据

### 06-运行方式.md
- 一句话摘要
- **环境要求**：Node ≥ 24（原因：靠 type stripping 免构建直接跑 `.ts`）
- **安装**：`playwright install firefox`
- **命令全表**：默认提问与全部子命令、选项
- **入口链**：`dsk.cmd` / `dsk` → `dskts-launch.mjs` → `src/dskts.ts`（并说明为何要 ASCII 转发桩）
- **环境变量**：`DSK_AGENT`、`DSKTS_NO_EXPLORER`、`DSKTS_REAL`、`DSK_LOG_STDIO`
- **落盘位置**：profile / lock / token / log / keeper 引导目录
- **典型工作流**：`up` → 提问 → `down`
- 依据

### 07-设计决策记录.md
ADR 风格，每条含「决策 / 背景 / 理由 / 代价 / 触发重开条件」：
- 用 Playwright 驱动持久 profile，而非官方 API 或桌面自动化
- 引入常驻 keeper，而非每次冷启动实例
- 完成判定用双信号，而非只看文本稳定
- 归属识别放在 CLI 侧，而非 keeper 侧
- 在会清理进程树的宿主里请 explorer 代启 keeper
- 手写私有帧协议，而非引入 RPC 库
- 帧带会话 token
- 删除默认只演练 + 前缀白名单
- 依据

### 08-安全模型与失败处理.md
- 一句话摘要
- **安全模型**：常驻 profile 的生命周期与 `down` 整删；token 把访问边界收到本用户（回环 TCP vs 文件 ACL）
- **三条硬规矩及其由来**（含导致「只认前缀」的那次误删事故）
- **失败模式表**：症状 / 根因 / 证据 / 处置 / 恢复
- 依据

### 09-验证体系与技术债.md
- 一句话摘要
- **三层验证**各自能证明什么、不能证明什么：离线测试 / 联网诊断 / 端到端
- **怎么跑**（命令）
- **已知软肋**：四个选择器失效点、单连接限制、服务条款风险
- **技术债**

- 依据

## 五、风险点与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| 行号漂移 | 源码一改，`#L12-L34` 全失真 | 以「文件 + 符号名」为主定位；行号只作辅助，不作唯一手段 |
| 双份腐化 | 文档复述常量/选择器，与源码不同步 | 不复述数值，统一指向 `constants.ts` |
| 信息重复 | 同一事实写在多章，改一处漏一处 | 单一事实源 + 相对链接引用 |
| 历史混淆 | 把 `output/`、`docs/` 的存档当现行事实 | 引用处强制标注「历史存档」 |
| 假设前置 | 默认读者懂 Playwright / Marionette / 帧协议 | 术语首次出现给定义；不预设自动化背景 |
| 章节膨胀 | 内容越写越多，维护成本上升 | 每章固定骨架 + 「不写的也写清楚」（非目标） |
| 准确性滑坡 | 未实测内容被当成实测 | 「未实测」为强制标注项，验收抽查 |
