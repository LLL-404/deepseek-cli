# 02 · 架构与时序

> 一句话摘要：CLI 与常驻 keeper 两个进程如何分工协作，一次提问从命令行到答案落 stdout 的完整经过。

## 术语速查

全篇统一用词，首次出现即按此义使用。

| 术语 | 含义 |
|---|---|
| **keeper** | 常驻进程，持有 Playwright 的浏览器持久上下文，在回环地址的固定端口上监听（端口见 `constants.ts` 的 `KEEPER_PORT`） |
| **CLI** | 每次调用产生的一次性命令行进程（`src/dskts.ts`） |
| **归属标记**（mark） | 会话标题前缀，形如 `WorkBuddy｜`，标识这条会话是哪个 Agent 开的 |
| **连续会话** | 每个 Agent 的默认会话，标题为 `<Agent 名>｜连续会话` |
| **帧**（frame） | CLI 与 keeper 之间的私有消息单元 |
| **一拍**（tick） | 判定循环的一次采样间隔，固定时长（见 `constants.ts` 的 `TICK_MS`） |
| **读数**（reading / sample） | 一拍从页面取到的三元组 `{text, busy, count}`；其中 `busy` 就是「页面是否仍挂着停止按钮」 |
| **双信号** | 判定「答完了」的两个条件同时成立：① 正文文本已停止变化（连续若干拍逐字相同，拍数阈值见 `constants.ts` 的 `STABLE_NEED`）；② 停止按钮已消失。二者缺一不可 |

## 双进程模型

```
调用方（人 / 脚本 / Agent）
        │  dskts "问题"
        ▼
   CLI 进程 · src/dskts.ts        ← 每次调用新建，用完退出
        │  私有帧 · 回环 TCP · 一命令一连接 · 串行
        ▼
   keeper 进程 · src/keeper.ts    ← 常驻，跨调用复用
        │  Playwright persistent context（有头）
        ▼
   Firefox + DeepSeek 网页版
```

**分工**：CLI 只负责参数解析、识别「这次是哪个 Agent」、连 keeper、收发帧、把结果写到 stdout/stderr 并映射退出码。所有需要页面的事（导航、填题、提交、读数、判定、改名、删除）都在 keeper 里做——因为它持有 `Page` 对象。

**为什么帧协议要串行**：keeper 只有一个浏览器上下文，不能同时跑两条页面流程。`busy` 标志位保证这一点：上一条还在处理时，新的命令立即收到 `busy` 并以退出码 2 返回，不排队。

## 为什么 keeper 必须常驻

根因是一条硬约束：**Playwright 的 Firefox 不支持二次连接已经启动的浏览器**。也就是说，进程一旦退出，下次就无法「接上」原来那个浏览器实例，只能重新启动。

如果每次调用都现起一个浏览器，冷启动成本（启动 Firefox + 加载页面 + 恢复会话）就会摊在**每一次问答**上。keeper 的存在把这件事变成一次性开销：

| 场景 | 表现 |
|---|---|
| 首次 `up` / 冷启动 | 起浏览器，较慢 |
| keeper 已在时的后续调用 | 热连接，连接与页面就绪约 3 秒（**不含模型生成本身的耗时**） |

keeper 由 `up` 显式启动、由 `down` 显式关闭，不做开机自启。

## 一次提问的完整时序

`dskts "问题"` 之后按下面的顺序走，任何一步不满足就带着证据停下。

### CLI 侧

| 步 | 动作 | 失败时 |
|---|---|---|
| 1 | 从 argv 或 stdin 读问题 | 空问题 → 退出码 1 |
| 2 | `resolveMark` 决定归属标记（`--mark` > `DSK_AGENT` > 环境特征 > `unknown`）。「环境特征」指调用方应用注入的进程级环境变量，完整规则表见 [04-关键函数与类型](./04-关键函数与类型.md) 的「归属识别」 | — |
| 3 | `ensureKeeper`：能连上就热连接，连不上就拉起并等端口就绪 | 拉不起 → 退出码 1 |
| 4 | 发 `checkLogin` 帧，确认已登录 | 未登录 → 退出码 2 |
| 5 | 开启 keeper 日志转发（轮询日志文件增量到本进程 stderr） | — |
| 6 | 发 `ask` 帧，带上问题、`--chat`、`maxWaitMs`、mark、附件绝对路径 | 超时/拒绝 → 按帧里的 code 映射 |

### keeper 侧（`askFlow`）

| 步 | 动作 | 失败时 |
|---|---|---|
| 7 | 若当前不在 chat 域名则导航过去 | — |
| 8 | `selectSession`：`--chat` 命中唯一则进；否则复用本 Agent 的连续会话；都没有就点「开启新对话」 | 命中 0 条或多条 → 退出码 2 |
| 9 | 进已有会话时留 2.5 秒，让「最后一条容器」稳定为上一答（否则快照会带着半渲染状态进判定）；新建会话时无需此步 | — |
| 10 | `setToggles`：把「深度思考」「智能搜索」设为目标状态，已是目标值则不动 | 找不到开关 → 只告警，继续 |
| 11 | `attachFile` 逐个挂附件，轮询文件名上屏 | 类型不在页面 `accept` 白名单 → 退出码 2；超时未见文件名 → 退出码 1 |
| 12 | `fillAndVerify`：填入问题后**回读输入框，必须逐字相等** | 不等 → 退出码 1 |
| 13 | `guardNotBusy`：页面若挂着「停止」按钮说明上一条还在生成，此时回车会被吃掉 | 忙 → 退出码 2 |
| 14 | `readOnce` 抓提交前快照 `count_before` / `last_before` | — |
| 15 | `submitWithVerify`：按回车提交，然后验证输入框已清空；没清空就补回车，最多 3 次 | 连吃 3 次 → 退出码 1 |
| 16 | `judgeLoop`：每拍读一次数喂给 `createJudge`，直到出现终态 | 见下 |
| 17 | 若终态是 `noRender`（提交后完全没看到新回合），刷新会话页重取一次 | 两轮都 `noRender` → 退出码 1，带 URL 与容器条数 |
| 18 | 从 URL 取会话 id；若是本次新建的会话，`renameTo` 改成连续会话标题 | 改名失败只记日志，不影响答案 |

### 判定终态

判定实际会产出**三种**终态（类型里还声明了第四种 `readsGaveUp`，但当前实现从不产生它——读数连续失败时直接按下面后两种收摊）：

| 终态 | 含义 | 对调用方的后果 |
|---|---|---|
| `done` | 双信号成立，答案完整 | 退出码 0 |
| `truncated` | 到 `--max-wait` 上限仍未判定完成，或读数连续多拍失败，但已拿到文本 | 返回文本 + `truncated` 标志 → 退出码 1 |
| `noRender` | 从未见到新回合（无渲染黑洞或被吞）；读数连续失败且一个字都没拿到也归此类 | 退出码 1，带证据报错 |

> `truncated` 与 `noRender` **都映射到退出码 1**——仅凭退出码分不出「答案可能不完整」与「根本没做成」，只能读 stderr 文案。这是已知技术债，见 [09-验证体系与技术债](./09-验证体系与技术债.md)。

### CLI 侧收尾

| 步 | 动作 |
|---|---|
| 19 | 有 `--out` 则把答案写文件（与 stdout 逐字一致） |
| 20 | `--stream` 模式下补打尚未输出的剩余文本，普通模式一次性打印答案 |
| 21 | 按 `truncated` 与帧的 `code` 映射退出码 |

## 三流契约

| 流 | 承载 | 说明 |
|---|---|---|
| **stdout** | 只有答案正文 | 脚本与管道只依赖这一条流；`--stream` 时是增量，结束后仍与整段模式逐字一致 |
| **stderr** | 全部过程日志 | 归属标记说明、keeper 日志实时转发（约每 500 毫秒轮询一次）、每拍进度（秒数/字数/状态）、警告 |
| **退出码** | 结果分类 | 0 成功 / 1 运行错误（含用法错、超时截断）/ 2 前提不满足（未登录、生成中、keeper 忙、命中不唯一、白名单拒绝）。逐条语义与映射规则以 [05-协议与接口契约](./05-协议与接口契约.md) 为准 |

## 磁盘状态布局

keeper 的运行状态全部落在 `%LOCALAPPDATA%` 下：独立 profile 目录（`dsk-ffprofile`）及其旁挂的锁、token、日志文件，另有一个 keeper 引导目录（仅 Windows explorer 代启路线使用）。

各文件的确切路径、由谁创建、由谁删除，见 [06-运行方式](./06-运行方式.md)——那里是这一节的**唯一事实源**，本节不重复列举。

设计取向是**不留业务状态**：会话列表不落盘，每次现读侧栏；唯一不得不落盘的是浏览器 profile 本身，因此它的生命周期被写死为「显式 `down` 整删」。
