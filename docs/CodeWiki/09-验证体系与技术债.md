# 09 · 验证体系与技术债

> 一句话摘要：现有验证各自能证明什么、还欠着什么、哪里最容易坏。

## 三层验证

三层**不能互相替代**：离线测试跑绿不等于真站点可用；诊断器读数正常也不等于判定逻辑正确。

| 层 | 位置 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| **离线测试** | [dskts/tests/](file:///d:/G/github/实用工具/DeepSeek命令行/dskts/tests) | 判定状态机的主要路径、帧编解码与坏帧处理、归属识别与命名规则 | 页面实际长什么样、选择器是否还有效 |
| **联网诊断** | [dskts/tools/](file:///d:/G/github/实用工具/DeepSeek命令行/dskts/tools) | 「现在这个页面还长这样」：容器条数、横幅隐藏前后字数差、两次读数是否一致、正文里有没有混进思考标记 | 判定逻辑是否正确 |
| **端到端** | 人工执行 | 唯一算数的判据：**stdout 逐字等于页面上人眼看到的答案** | 覆盖面（只能人工抽验） |

## 怎么跑

```
cd dskts

npx tsc --noEmit              # 类型检查（应 0 错误）
node tests/judge.test.ts      # 离线测试
node tests/frame.test.ts
node tests/agent.test.ts

node tools/probe_prime.ts     # 联网诊断（会自己起环境）
node tools/probe.ts
```

离线测试全程不启动浏览器，可随时跑；联网诊断需要能连上 DeepSeek 网页版。

## 已知软肋

1. **取词依赖页面 DOM 类名**。具体是四个点最容易因改版失效：正文容器、思考容器、代码块横幅、以及「停止」按钮的判据。它们失效时不一定报错——可能表现为「取到空文本」或「判定迟迟不结束」，所以诊断器要先跑。
2. **一次只允许一条自动化连接**。keeper 只有一个浏览器上下文，第二条命令会拿到「忙」。两个终端同时跑会互相干扰。
3. **导航到已有会话后有一段固定等待**——进会话后固定等 2.5 秒再抓快照，用于让「最后一条容器」稳定为上一答。这段时长是否够用**未做实测**；若不够，提交前快照会带上半渲染状态，进而干扰判定。
4. **不再有后备实现**。早期保留的 Python 版已于 2026-10-07 移除，上面这些软肋现在就是整个工具的软肋。
5. **服务条款风险**。自动化的是你自己已登录的网页界面，账号被限制或静默降级的风险由使用者自负。

## 技术债

| # | 债 | 说明 | 状态 |
|---|---|---|---|
| 1 | `Terminal` 里的 `readsGaveUp` 从未被产出 | 类型声明了四种终态，实现只产生三种（详见 [04-关键函数与类型](./04-关键函数与类型.md)） | 死类型，可删 |
| 2 | `ping` 无任何调用方 | keeper 侧实现了 `ping`，但 `dskts.ts` 与 `tools/` 都不用它（`probe` / `diag` 有 tools 脚本调用，不算死代码） | 死命令，可删 |
| 3 | 日志可能无界增长 | 日志轮转逻辑在「keeper 自行落盘」的模式下生效；常规启动路径把 stdio 直接指向日志文件，会跳过轮转（**按代码推得，未实测**） | 待验证 |
| 4 | 编排层职责偏离 | 早期设计把编排放在 CLI 侧，实际落在 keeper 侧；不改也能跑，但设计文档与实现不一致 | 已记录，未重构 |
| 5 | `dsk` 命令名未移交 | PATH 上的入口桩仍指向已删除的旧实现，当前需要用 `dskts` 调用 | 见根 README 待办 |
| 6 | 没有 `--new` | 想另开一条会话，只能靠删掉当前连续会话或指定 `--chat` | 设计取舍 |
| 7 | 开关不可关闭 | 深度思考与智能搜索默认全开且无关闭选项 | 设计取舍 |
| 8 | 截断与失败共用退出码 1 | 调用方仅凭退出码无法区分「答案可能被截断」与「根本没做成」，只能读 stderr 文案；早期实现曾用独立退出码区分这两者 | 待解决 |

## 已搁置的扩展路线

曾规划过一条替代路线：**改用浏览器扩展 + Native Messaging**，直接读取页面自己发出的响应流，而不是从 DOM 里取词。

| 它原本要解决的问题 | 现状 |
|---|---|
| 凭据落盘 | **已解决**——常驻 profile + 显式 `down` 整删 |
| 冷启动慢 | **已解决**——keeper 常驻 + 热连接 |
| 从 DOM 取词、改版要重摸 | **未解决**，但暂不构成换路线的理由 |

**触发重开的条件**：响应流拿不到，或选择器频繁失效。

另有一项评估结论：**暂不从主浏览器 profile 导入 cookies**。技术上可行（Firefox 的 cookies 库是明文存储，复制目标域的行即可），但代价不划算——需要主浏览器完全退出才能读库、两端版本与 schema 可能不一致，而当前 profile 的登录成本已经一次性付掉了。触发条件：重新登录的成本再次显著抬高（如账号切换频繁）。
