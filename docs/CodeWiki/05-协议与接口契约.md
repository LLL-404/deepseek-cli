# 05 · 协议与接口契约

> 一句话摘要：CLI 与 keeper 之间的私有帧协议、认证方式、命令面与退出码语义。

## 帧格式

CLI 与 keeper 之间走一条极简私有协议，跑在回环 TCP 上：

```
[ 4 字节 · 大端序 · 帧体长度 N ][ N 字节 · UTF-8 JSON 帧体 ]
```

| 方向 | 形状 |
|---|---|
| 请求 | `{ op: string, params?: unknown, token?: string }` |
| 响应 | `{ ok: true, data: T }` 或 `{ ok: false, error: string, code: number }` |
| 进度响应 | 在成功帧上加 `progress: true` |

**一连接一命令**：客户端连上即写一帧，收到第一个**非进度**响应帧就结算并断开；keeper 处理完即回帧，不保持长连接。

## 帧体上限与坏帧处置

| 机制 | 规则 |
|---|---|
| 帧体上限 | 由 [frame.ts](file:///d:/G/github/实用工具/DeepSeek命令行/dskts/src/frame.ts) 里的 `FRAME_MAX_BYTES` 限定。超限不预分配内存，直接判为坏帧 |
| 非法 JSON | 解码器抛 `FrameError`，不回显原始字节（防往日志里注入控制字符） |
| 形状校验 | 帧体必须是「对象、非数组、`op` 是字符串」，否则按坏帧 |
| 原型链防护 | 取处理函数用 `Object.hasOwn`，避免 `constructor` / `toString` 这类原型链成员被当成命令 |
| 处置方式 | 一律**只断这条连接、不杀进程**：先回一帧错误说明，再销毁 socket |

> 这套校验来自一次实弹事故：早期版本里一个 5 字节畸形帧就能打死 keeper——非法 JSON、帧体形状、原型链 `op` 三个向量叠加。修复后，坏帧只影响它自己那条连接。

## token 门卫

| 环节 | 行为 |
|---|---|
| 生成 | keeper 每次启动生成一个新的随机 token，与 keeper 进程同生命周期 |
| 存放 | 写到 profile 目录旁的 `.token` 文件，权限为仅本用户可读 |
| 携带 | CLI 每一帧都带上（从该文件读取） |
| 校验 | 不符即拒：回一帧错误说明并断开，**不泄露 token 值** |

**它防什么、不防什么**：回环 TCP 对同机**所有账户**开放，而 `%LOCALAPPDATA%` 下的文件受用户 ACL 保护。所以这道门卫的作用是把访问边界从「全机」收到「本用户」；同一用户下的进程本来就能读那个文件、也能做任何事，不在防护范围内。

读不到 token 文件时 CLI 会发空 token，被 keeper 明确拒绝并提示重启 keeper。

## 命令表

keeper 侧的处理函数表（来源 [keeper.ts](file:///d:/G/github/实用工具/DeepSeek命令行/dskts/src/keeper.ts) 的 `handlers`）：

| op | params | 返回 | CLI 入口 |
|---|---|---|---|
| `ping` | — | `{ pid }` | 无（见下方说明） |
| `status` | — | `{ pid, browser, url, loggedIn }` | `dskts status` |
| `up` | — | `{ url }` | `dskts up` |
| `checkLogin` | — | `{ loggedIn, url }` | `dskts` 提问前自动调用 |

| `probe` | `{ mark }` | `ProbeReport` | 无（由 `tools/probe.ts` 调用） |
| `diag` | — | 诊断对象 | 无（由 `tools/diag.ts` 调用） |
| `down` | — | `{ profileDeleted }` | `dskts down` |

**关于没有 `dskts` 子命令的三个命令**：`probe` 与 `diag` 由 `tools/` 下的独立脚本直接按帧调用（[probe.ts](file:///d:/G/github/实用工具/DeepSeek命令行/dskts/tools/probe.ts)、[diag.ts](file:///d:/G/github/实用工具/DeepSeek命令行/dskts/tools/diag.ts)），只是没有暴露成 `dskts` 子命令；`ping` 目前没有任何调用方——只在帧编解码的测试里作为样例 `op` 出现。

## 进度帧与 `--stream`

`ask` 是唯一会发进度帧的命令：keeper 侧在判定循环的每一拍通过 `emit` 发出一帧 `{ ok: true, data, progress: true }`，`data` 形如 `{ type: "delta", text }` 或 `{ type: "reset", text }`。

CLI 的 `rpc` 把进度帧交给 `onProgress`；只有 `--stream` 时才注册这个回调，把增量写到 stdout。增量假设文本只增不减，一旦发现变短就发 `reset` 全量重建。无论是否 `--stream`，最终答案帧都会照常返回。

## 退出码契约

| 码 | 常量 | 含义 |
|---|---|---|
| `0` | `EXIT_OK` | 拿到答案且判定写完 |
| `1` | `EXIT_ERROR` | 运行错误：用法错、连不上 keeper、环境没起来、提交失败、超时截断 |
| `2` | `EXIT_PREREQ` | 前提不满足：未登录、上一条仍在生成、keeper 忙、`--chat` 命中 0 条或多条、附件类型被白名单拒绝、`rm` 拒绝 |

**映射规则**：CLI 收到失败帧时，`code === 2` 映射为 `2`，其余一律映射为 `1`。

`FlowError` 是页面层的错误类型，构造时默认 `code = 1`；需要表达「前提不满足」的地方显式传 `2`。这样页面层不必知道退出码常量，只表达语义。

## 并发语义

| 约束 | 实现方式 |
|---|---|
| keeper 单实例 | 端口独占：第二个 keeper 监听失败即静默退出 |
| 命令串行 | `busy` 标志位；上一条未处理完时新命令立即收到 `busy` 帧（`code 2`），**不排队** |
| 一条命令一条连接 | 连接不跨命令复用 |

因此两个终端同时跑会互相干扰：后来的那条只能拿到「忙」。这是刻意的取舍——只有一个浏览器上下文，排队会让等待时间不可预测。
