# 08 · 安全模型与失败处理

> 一句话摘要：凭据与访问边界怎么管，以及出问题时是什么症状、怎么恢复。

## 安全模型

### 凭据：常驻 profile，显式整删

登录态存在一个**独立浏览器 profile 目录**里（路径见 [06-运行方式](./06-运行方式.md) 的「落盘位置」）。它的生命周期被写死成两步：

| 阶段 | 行为 |
|---|---|
| 建立 | 首次 `dskts up` 时在弹出的窗口里登录一次，登录态写入该 profile |
| 使用 | 之后每次调用复用同一 profile，**不再需要登录** |
| 销毁 | `dskts down` 关闭浏览器并**删除整个 profile 目录**（含全部登录态），同时清掉锁与 token |

这是相对早期实现的**安全模型变化**：以前是「每次复制一份 profile 副本、用完必删」，代价是每次都要清理、强杀或断电时可能残留；现在改成常驻 + 显式销毁，代价是**凭据会一直躺在盘上，直到你主动 `down`**。

profile 目录是这套工具**唯一需要刻意保护的对象**——里面有完整登录态。

### 访问边界：token 把范围收到本用户

keeper 监听的端口在回环地址上，**同机所有账户都能连**。因此在连接之上加了一道 token 门卫（生成、存放、校验见 [05-协议与接口契约](./05-协议与接口契约.md)）。

它借助的是文件系统 ACL：`%LOCALAPPDATA%` 下的文件只有本用户可读。所以这道门卫把访问边界从「全机所有账户」收窄到「本用户」——**同一个用户下的其它进程本来就能读那个 token 文件、也能做任何事，不在防护范围内**。

### 进程管理：按标记精确匹配

清扫残留进程时用的是**「进程名 + 命令行标记」双重匹配**：火狐要求命令行里带着本工具的 profile 目录名，keeper 要求带着专用进程标记。**绝不按裸字符串全局匹配**。

这条纪律有实际代价：曾经出现过「命令行里恰好带上 profile 名的祖先进程被误杀」的事故。所以规则是——两个条件都成立才动手。

## 三条硬规矩及其由来

| 规矩 | 由来 |
|---|---|
| **不外发正文与未公开设定**——只发工具用法、报错原文、通用技术问题 | 工具会接触到你与模型的对话内容；这类内容外发出去无法收回 |
| **不伪造反爬令牌，不在浏览器之外重放会话凭据** | 这条路自动化的是**你自己已登录的网页界面**，未必符合站点服务条款。能观测页面自己发出的行为，但不能替页面签名；账号被限制或静默降级的风险由使用者自负 |
| **删除只认已知前缀，且默认只演练** | 早期版本用正文关键词判断会话归属，**误删了作者自己的两条会话**。此后归属判定只认显式前缀，越权必须显式加参数 |

前两条是设计边界，第三条是事故后立的规则——它是唯一一条**因真实损失**而引入的约束。

## 失败模式表

| 症状 | 根因 | 处置 | 恢复 |
|---|---|---|---|
| 等待中途连接中断 | 另一条会话执行了 `down`，把 keeper 与浏览器一起收走 | 直接报错 | 重跑；动手前先 `status` 看一眼 |
| 问题发出去了却没有新回合 | 上一条仍在生成时，回车被页面吃掉 | 提交前检查是否仍在生成（`guardNotBusy`），是则退 2 | 等上一条答完再问 |
| 提交后完全没见到新回合 | 偶发的无渲染情况 | 刷新会话页重取一次；仍失败则带当前 URL 与容器条数报错，**绝不静默返回空答案** | 重试；若频繁出现，跑联网诊断器 |
| 答案可能被截断 | 到达等待上限仍未判定完成 | 返回已拿到的文本并置 `truncated` 标志，退出码 1 | 加大等待上限重问 |
| 改名没生效，但答案正常 | 行菜单与编辑框的时序问题 | 只记日志，不影响答案返回 | 手动改名 |
| 取不到答案、且容器条数为 0 | 页面改版导致选择器失效 | 报错并带上当前 URL | 跑联网诊断器重探选择器（见 [09-验证体系与技术债](./09-验证体系与技术债.md)） |
| 取到没渲染完的页面 | 导航后是固定等待而非条件等待 | 报错并带当前 URL 与页面开头文字 | 慢网络下重跑 |
| 提示未登录 | profile 被 `down` 删除，或登录态失效 | 退出码 2 | 跑 `dskts up` 在窗口里登录 |
| 提示 keeper 忙 | 另一条命令正在处理 | 立即返回，**不排队** | 等前一条结束再试 |
| keeper 与浏览器在命令结束后一起消失 | 宿主按快照清理了这条命令产生的全部进程 | 改由 explorer 代启 keeper（见 [07-设计决策记录](./07-设计决策记录.md) D5） | 或先在系统终端里手动 `up` 起一次 |

**两个「不静默」原则**贯穿全表：拿不到答案时报错并附证据（URL、容器条数、是否仍在生成），绝不返回空答案冒充成功；答案可能不完整时用 `truncated` 标志与退出码明确告知，而不是假装完整。

> 本表综合项目记录与代码路径整理。其中「宿主快照式清理」「无渲染」「改名失效」等行有项目留存的实测支撑，其余各行是按代码路径推得的**可能**失败模式，未在现版上逐条复现。
