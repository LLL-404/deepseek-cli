# Code Wiki 需求梳理（dskts）

> 阶段产物 · Phase 1 / 4
> 对象项目：`实用工具/DeepSeek命令行`（仅覆盖 TS 主线 `dskts/`）

## 一、核心目标（一句话）

为 `dskts`（DeepSeek 网页版命令行，TypeScript + Playwright 双进程实现）产出一套结构化 Code Wiki，让**未读过源码的新读者或 AI Agent** 能在一份文档内建立完整心智模型：它是什么、怎么跑、由哪些模块组成、关键函数各自负责什么、模块间如何依赖、以及改哪里会牵动哪里。

## 二、目标用户与场景

| 用户 | 场景 | 期望从文档获得 |
|---|---|---|
| 新接手者 / 未来的作者 | 隔一段时间回到项目 | 30 分钟内重建架构认知，知道入口在哪、改一处要动哪几处 |
| 其他 Agent（WorkBuddy / Qoder / Trae 等） | 要调用 dsk 能力 | 命令表、退出码契约、stdin/stdout 流契约 |
| 代码评审者 | 评审改动 | 分层边界、职责表、已知技术债清单 |
| 自动化检索 | 全文搜索 | 文件名/函数名可被直接命中（采用真实标识符作标题） |

## 四、边界约束（明确不做）

**覆盖范围**
- 只写当前实现（`dskts/`）。原 Python/Marionette 版代码及其设计文档已于 2026-10-07 移除，仅在「项目概览」记一句历史沿革，不展开其设计。
- 不展开已搁置的扩展路线（Edge 扩展 + Native Messaging），仅在演进一节记一句「已搁置 + 重开条件」。
- `output/`、`docs/` 里的是历史存档（迁移规划件、外部评审原文、技术笔记），引用时标明其为历史记录，不当作现行文档。

**内容纪律**
- 不改动任何源码；本任务只产出文档。
- 不整段复制源码，关键处给**短代码片段 + 文件行号链接**，避免文档与代码双份腐化。
- 事实必须可追溯：凡写进文档的结论都要能落到具体文件/行为依据；未实测的标「未实测」（沿用项目既有习惯）。
- 不重复项目已有的 `README.md` / `dskts/README.md` / `DESIGN.md` 原文，而是**重组为面向读者的结构与索引**。

**形式约束**
- 语言：中文（与项目既有文档一致）。
- 形态：多文件（索引 + 分章节），落在 `docs/CodeWiki/`。
- 与旧规划件隔离：不覆盖 `output/plan_phase*.md`。

## 五、验收标准

1. 覆盖清单中全部 P0 项，P1 项至少 90%，P2 项按可用信息尽力覆盖。
2. 每个模块章节都能回答「它负责什么 / 它依赖谁 / 谁依赖它 / 改它的风险」。
3. 文档中出现的每个文件名与函数名，都能在源码中精确定位（链接可用）。
4. 一个没读过源码的人只读索引 + 概览 + 架构三章，能说出这个项目「为什么必须有两个进程」。
5. 不出现与源码矛盾的描述；不确定处显式标注。
