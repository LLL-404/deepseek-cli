## 它的回答（全文照录）

下面按你五问来，只谈机制、每条路的代价和失效条件。

一、1 步与 N 步之间的分段策略

（按弱执行器前提评分。注：弱执行器无法自己判断"是不是该停"，所以任何策略都必须在 EXEC 里写成机械规则，不能写成"视情况"。）

A. 依赖边界分批。 只把彼此无共享状态的步骤编成一批，一旦某步输出是后几步的输入，就在此切块。代价：要求提前知道依赖图，而你看不到机器，依赖只能靠猜。失效条件：隐藏耦合（步 2 意外改了步 4 读的文件、步 1 改了 CWD、步 1 改了环境变量）。弱执行器对此完全无感。

B. 只读批次 + 变更单跑。 只读命令任意成批；每个会写/改/删的命令单独执行，跑完必停。代价：往返次数大增（每轮约 1–3 分钟）。失效条件：有些"看起来只读"的命令不纯（缓存预热、日志轮转、触发索引、改 mtime）。而且"是否只读"由谁判？只能是你在 EXEC 里显式标。

C. 固定小批（3–4 步）+ 每步哨兵。 每步自带一个唯一标记和退出码回显，批内任意一步失败整批中止。代价：需要弱执行器真的会跑这个循环——多数"只会复制粘贴"的执行器做不到。失效条件：执行器要么忽略哨兵继续跑，要么一见到哨兵就停错地方。

D. 输出预算分批。 累计输出达到约 2000 字就停，保证简报不撞上限。代价：事前无法估算，执行器也估不了。失效条件：一条命令喷 1MB，预算机制根本来不及。

E. 阶段分批。 侦察一批、构建一批、验证一批。代价：阶段边界是主观的，弱执行器也识别不了"我现在在哪个阶段"。

给弱执行器最稳的形态：C 的变体，但批次大小固定为 3，且只在"你事先声明的依赖切换点"才允许跨批。不依赖执行器聪明，只依赖它在固定步数后停——这是它唯一能可靠执行的规则。

回滚由谁定。 三条路：

你在 EXEC 里预先写 ON_FAIL: 行，紧跟每个变更步骤。执行器机械照跑。代价：占用 EXEC 预算、无法覆盖未知失败。失效条件：失败模式和你预想的不是一种。

本地停下再问你。代价：一次完整往返。失效条件：同一个错误重复出现，每次往返都白花。

最便宜的一条：变更前快照。 每个变更步骤前面加一行"把目标拷到 .snap/"，失败时反向 mv 回去。代价：磁盘和时间；弱执行器只需照抄两行 mv。失效条件：磁盘满、被改的是工作目录外的东西。

对弱执行器，我倾向快照 + ON_FAIL 兜底，因为两者都能写成固定命令行，不依赖判断。

二、EXPECT 五种形式的漏判坑

你漏掉的最要命的一条：包含:X 匹配的是命令的原始输出，而原始输出里往往已经含有错误信息。命令失败时 stderr 也含 "error" 之类词，可能恰好包含你写的 X。结构上更硬的做法是让 EXPECT 检查你自己注入的哨兵，而不是检查命令的自然输出：每条命令尾巴追加 & echo __R1_OK__，EXPECT 只写 包含:__R1_OK__。这样"命令没走完"和"命令输出变了"是两种可区分的失败，而不是混成一种。

其余常见坑：

编码：cmd 里 chcp 65001 只影响之后新起的进程，某些老工具仍吐 GBK。包含:中文 会在字节边界上失败。

换行：CRLF 拼进子串，包含:X\r 和 包含:X 是两回事。

大小写：cmd 的 find 默认不敏感，grep 敏感。执行器若不做归一，会随命令不同而变。

多行子串：包含: 通常按单行匹配，跨行就落空。

计数缺失：无法表达"X 恰好出现一次"。多次命中一律算过。

顺序缺失：包含:A + 包含:B 约束不到"A 在 B 之前"。

stdout/stderr 混合：合并检查会从无害警告里命中；分开检查又要求执行器知道哪路是哪路。

exit=N 的管道陷阱：cmd.exe 里管道和 & 的 ERRORLEVEL 语义反直觉，前一条命令失败不影响后一条，整行退出码只反映最后一段。

正则：BRE / ERE / PCRE 各不相同，弱执行器实现哪一种都不确定；而且多字节字符下按字节做 . 匹配会乱套。

非空 太弱：dir 在空目录也输出"找不到文件"，仍是非空。

"未判定"继续跑 vs 停。 取决于下一步是不是变更操作。若下一步只读，继续跑没风险；若下一步会写/删/改，继续跑就是基于错假设动手。所以建议："未判定"一律视为"这一步没确认成功"，触发 EXEC 里为该步预置的 ON_FAIL，而不是简单地 rc=0 就往下。既不浪费整轮往返，也不让未确认的步骤走进变更区。

防止 EXPECT 与 CMD 实际输出格式不一致。 唯一稳的办法是让 EXPECT 不再依赖命令的自然输出——只用哨兵、退出码，以及你自己注入的字段。举例：

cmd ; echo __R3_DONE__ ; echo __R3_RC=%ERRORLEVEL%
EXPECT: 包含:__R3_DONE__ 包含:__R3_RC=0

这样命令输出换了排序、加了警告、语言变了都不影响判定，只有"根本没执行到这一句"或"退出码非 0"两种真失败会被抓到。

三、STATE 膨胀：全量、差异、第三种

差异式记忆必然崩坏的三种条件：

本地持久化本身出过一次事故（半写、覆盖前断电、手动编辑、工作目录变了导致找不到旧状态）；

你在某轮改了 STATE 的字段名或结构，而本地还按旧 schema 应用差异；

本地执行器对某一步的摘要丢了行（终端回显吞行之类），差异应用到错基线上。

三种都不可自查——执行器是弱模型，它不会发现"自己的状态看起来不对"。所以差异式在你这个约束下不能用。

第三种压缩法：分层 + 固定 schema + 只追加日志。

头部：目标 / 环境 / 当前假设 / 当前阶段，固定字段、固定预算（比如 1200 字），每轮你全量重写。超出预算就写失败，逼你压缩。

尾部：最近 N 轮（比如 3 轮），滚动窗口。

已完成项折叠成计数：已折叠：第 1–47 轮，共 47 步，最终确认结果：<一句>。折叠点由你选，但一旦折叠就不能再展开，所以只折叠"确定不会再回头"的步骤。

本地侧另存一份只追加的 trace.log，人可读，但不进简报。它只是证据，不是状态。

判定成本：头部每轮是一次压缩判断（约等于你在写简报时多花一点 token）；尾部滑出窗口时你要决定"折叠还是丢弃"，这是实质判断，没法机械做；只追加日志零成本，但只有人去看才有用。

比纯全量省预算，比纯差异抗漂移。代价是：折叠点选错（过早折叠掉一条后面还要用的结论），你只能靠 trace.log 人工补，而 trace.log 不进简报，你按设计看不到它——所以折叠时宁晚不早。

四、危险闸门：并集之外

并集之外的可选组合：

按类别并集：删除 / 覆盖 / 支付 / 对外发送 / 装软件 / 改系统设置 / 杀进程 / 丢工作区 → 并集。网络请求（curl/wget）→ 你标 yes 就停，标 no 时扫描命中仍要停下来问，但可以让"扫描原因"占主导，因为同名的 find/curl 在不同 PATH 下含义不同。

带理由否决：扫描命中时若你能给出"为什么这条看起来危险其实是安全的"具体理由，允许降级为"问一次"。代价：你一旦判错，闸门失效。不建议。

三级制：你标 block / ask / allow，扫描也出三级，取 max。代价：多一级语义，弱执行器要多实现一个分支。

两种不一致怎么处理：

(a) 你标 yes、扫描干净：停、问人。但把你标 yes 的理由一并写进 EXEC，让用户看理由决定，而不是无理由打断。这是把误报成本从"白打断一次"降到"用户看一眼就能放行"。

(b) 你标 no、扫描命中：扫描赢，停下来问。同时把"扫描命中的关键词"和"你判 no 的理由"都给用户看。因为扫描是底线，它抓的就是你忽略的写法；忽略它的代价比多问一次大得多。

在"单行字符串交给 shell"约束下，结构上更硬的做法：

参数化白名单：不看命令文本整体，先解析出可执行文件名（第一个 token），只放行一份固定的可执行文件白名单。这比关键词黑名单硬，因为绕过黑名单靠改写法，绕过白名单只能换命令名。

路径强制：扫描该行里所有像路径的 token，任何路径必须落在工作目录内。这条比关键词硬得多——它把"读盘外泄"和"误删别处"两个大类一并挡住，且和改写无关。

变更前快照：任何会修改文件的命令执行前先备份目标目录。这样"坏命令"的最坏代价变成"浪费磁盘和时间"，而不是"丢数据"。

只追加的审计：每轮一行写进独立日志文件，从不重写。人不看时它是死文件，人一翻就能重建发生了什么。

关键词扫描能改写法绕过这件事，在这个约束下不能靠"更聪明的正则"解决，只能靠"白名单 + 路径强制"把可绕过面收窄。剩下的绕过面（例如某白名单命令本身的某个参数行为）只能靠快照和人工复查兜。

五、你该问的第五件事

不是你问的四个方向错了，是前提里有一条对你的设计影响最大：

"你在每轮重写 STATE"这条假设，如果本地覆盖失败就会静默丢信息。 弱执行器只会 writeFile，不会"写临时文件再 rename"。所以要么 EXEC 里强制两步（先写 .new 再 mv 覆盖），要么接受"STATE 可能在某轮被写半截"。这条比简报字数、比 EXPECT 形式都更容易一夜之间让你丢好几轮记忆。

另外一条我认为被低估的："步骤失败"和"步骤不可判定"是两种成本完全不同的东西，但你的设计目前把它们混在一起。失败有原始输出可回传；不可判定往往意味着输出被吞、编码错、命令没跑全——这些恰恰是最可能连续复现的失败。所以"未判定"应该触发换一种探测方式重试一次，而不是简单把输出回传。否则你会连续几轮在同一个不可判定上打转。

其余的（分工、STATE 重写、DANGER 自标）大体成立，只有"DANGER 由你标"这一条我建议改成：你标"变更/非变更"，本地标"危险/非危险"。你标 DANGER 时看不到命令在本地的真实解析路径，标得再准也是意图层面的；本地扫描虽粗，但它看的是本机实际要跑的那串字节。两者各看一半，比让同一方两头都看要稳。

## 我的逐条判断（含本仓复测）

外部回答只当线索。下面每条都标了「采纳 / 当线索 / 否决」，凡涉及机制是否真成立的，都给了在本仓跑出来的命令与输出。

### 采纳，并且推翻了他的写法

**1. 哨兵式 EXPECT：方向对，`&` 是错的，必须 `&&`。**
他建议「每条命令尾巴追加 `& echo __R1_OK__`」。按 `bridge.ts` 的真实 argv 规则（`cmd.exe /d /s /c "chcp 65001>nul&&<CMD>"`，`windowsVerbatimArguments`）实测五条，见 `dskts/tools/probe_cmd_sentinel.mjs`：

| 内层命令 | cmd 退出码 | stdout |
|---|---|---|
| `node -e "console.log(1)" & echo __R1_OK__` | 0 | `1` + `__R1_OK__` |
| `node -e "process.exit(3)" & echo __AFTER__` | **0** | **`__AFTER__`** |
| `node -e "console.log(1)" && echo __RC=%ERRORLEVEL%` | 0 | `__RC=0` |
| `node -e "process.exit(3)" && echo __NO__` | 3 | （空） |
| `node -e "process.exit(3)" \| more & echo __RC2=%ERRORLEVEL%` | **0** | **`__RC2=0`** |

第二行就是要命的那条：**真命令退 3，`&` 后面的哨兵照样打印，整行退出码还是 0**——照他写的哨兵分不出成败。第四行才是可用形态：`&&` 之后的哨兵只在成功时出现。
第三、五行还顺带否掉一种写法：`%ERRORLEVEL%` 在单行里是**解析期**展开，读到的永远是这一行开始前的值；管道之后它只反映最后一段。所以 `exit=N` 这类预期，只在「这一行没有任何 `&` 链接」时可信。
落到实现：顾问提示词里给这条固定写法 `CMD: <命令> && echo __R3_OK__` + `EXPECT: 包含:__R3_OK__`，并明写「不要用 `& echo`，不要用 `%ERRORLEVEL%`」。

**2. 「未判定」不能等于继续跑。** 我原计划 rc=0 就继续；他这条说中要害——不可判定常常就是字节层面的事（编码、CRLF、行被吞），而这类问题会连续复现。改为：**未判定视为未确认，立即停本批**，简报里原样标注「第 k 步 EXPECT 无法机械判定」，让顾问下一轮收紧形式。代价是顾问必须写机械 EXPECT，所以提示词里必须把五种形式写在前面。

**3. `state.md` 的覆盖写必须是原子的。** 他盲猜中了一次真风险：弱执行器只会 `writeFile`，写一半断电就静默丢好几轮记忆。本仓复测：`fs.renameSync` 在 Windows 上**能覆盖已存在的目标文件**（临时目录实测输出 `rename 覆盖 OK, 现内容= NEW`），所以「写 `.tmp` 再 rename」这条路可用。落到实现：`writeState` 改成 tmp+rename。

### 采纳（与我原设计本就一致，等于被独立确认）

**4. 分层记忆**：固定 schema 的头部每轮全量重写、尾部滑窗、已完成项折叠成计数、另存一份只追加但不进简报的 trace。这正是 `state.md` 两区（顾问记忆整块覆盖 / 轮次记录只追加）+ 简报只带最近 3 轮的形状。他补的「折叠宁晚不早」是对的，写进 BRIDGE.md。

**5. 闸门不一致的处理**：并集；`yes`+扫描干净 → 停，并把标注理由一起给人看；`no`+扫描命中 → **扫描赢**，同时把命中关键词和他判 no 的理由并列展示。误报的代价是白打断一次，漏拦的代价是丢数据。

### 否决（带理由，不实现）

**6. 「可执行文件白名单」**：这条工具的全部用途就是跑任意本地命令，收窄成固定清单等于换掉它。

**7. 「行内所有像路径的 token 必须落在工作目录内」**：误拦率会把工具废掉——本仓已有同类教训（`2>nul`、`>/dev/null`、`2>&1` 两次实弹误拦）。已有的围栏在 `read_file`/`python`/`write_file` 三个动作上，`shell` 这条不做。

**8. 变更前自动快照**：那要新增一套快照目录与恢复语义，是另一个功能。现在的兜底是每步落 `state.md`、危险动作一律交回给人。

**9. 三级 `block/ask/allow`**：多一级语义就要弱模型多一个分支，和「防呆」相冲。

**10. 把 `DANGER` 拆成两根轴（顾问标变更/非变更，本地标危险/非危险）**：道理成立，但作者规格把字段钉死为 `DANGER: no|yes`，改名会让执行器与规格对不上。留在此处记录，不动字段。

### 这轮问答改变了什么

一句话：**没改变分工，改变了两处写法**（哨兵必须 `&&`、未判定即停），并补了一处真风险（`state.md` 原子写）。这三条全部进 P2 的实现，不进「以后再说」。
