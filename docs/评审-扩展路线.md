一、这条路的已知致命坑
1. --load-extension 在 Chromium 上的现状

能用，但脆弱。

Chrome/Edge 的 --load-extension 仍然可用，加载未打包扩展需要开发者模式或命令行开关。但企业策略可以完全禁止未签名扩展安装，管理员通过组策略配置 ExtensionInstallBlocklist 或限制开发者模式后，--load-extension 会被直接拦掉。在 Windows 上这是系统级组策略，不是浏览器设置里能绕过的。-
3

更麻烦的是 Edge：Edge 跟随 Chromium 的策略框架，企业环境下的 Edge 组策略比 Chrome 更常见。如果你的机器被域管或者装了 Intune 策略，--load-extension 可能静默失效——扩展不加载，但浏览器正常启动，你的命令行工具拿不到任何响应。

实际影响：个人机器通常没事。但你需要一个启动时的健康检查：启动后确认扩展的 service worker 确实起来了，而不是假设它加载了。

2. MV3 内容脚本注入主世界的时机

用 world: "MAIN" + run_at: "document_start" 可以赶在页面脚本之前。

这是 MV3 引入 MAIN world 的核心用途。Chromium 保证 MAIN world 的 document_start 脚本在页面任何 <script> 之前执行，没有竞态-
。关键是不能用老的 <script> 标签注入法——那种方式异步加载，会跑在页面脚本之后-
。

但有两个真实的失败模式：

第一，页面可能在早期脚本里就保存了 fetch 的引用。 如果目标站点的入口脚本在 <head> 最前面执行 const _fetch = window.fetch，你的 MAIN world 脚本必须在那个脚本之前把 window.fetch 替换掉。document_start 在 Chromium 里确实能保证这个顺序，但前提是扩展的 content script 注册在 document_start，且 service worker 已经就绪。如果 service worker 冷启动，注册流程可能延迟，你的脚本就晚了。

第二，MAIN world 脚本即使包住了 fetch，也会被 toString() 检测。 一个被包装的 fetch 函数，window.fetch.toString() 不会返回 [native code]。ES6 Proxy 可以伪造 toString，但 Proxy 本身又有其他可检测特征-
。如果站点做了完整性校验，你的 hook 会被发现。这不是“能不能包住”的问题，是“包住之后能不能不被发现”的问题。

3. Service Worker 空闲休眠与 Native Messaging 端口

Native Messaging 连接确实可以保活 service worker，但有条件。

Chrome 105+ 的行为是：只要 service worker 通过 chrome.runtime.connectNative 保持了一个打开的 port，service worker 就不会被当作空闲卸载-
。Chrome 官方迁移文档也确认原生消息传递是“使 service worker 保持活动状态超过 5 分钟”的选定情形之一。

但坑在于：如果 native host 进程退出，port 断开，service worker 就失去保活依据。你需要让 native host 不要轻易退出，或者在 port 断开时立即重连。另一个坑是 service worker 本身可能因为更新、浏览器重启等原因被重新加载，你的 port 变量会丢失，需要重新 connectNative。

实际影响：对于“命令行发一个请求、拿答案、退出”的短生命周期场景，这个问题不严重——命令执行期间 port 保持打开就够了。如果你要长时间后台常驻，才需要认真处理重连。

4. 流式响应的压缩与分块重组

如果你 hook 的是 fetch，你在 response body 层面拿到的是解压后的数据。

fetch 返回的 Response.body 是一个 ReadableStream，浏览器已经处理了 Content-Encoding（gzip/br）和 Transfer-Encoding: chunked。你读到的 chunk 是解码后的字节，不需要自己处理压缩。但 chunk 的边界不等于消息的边界——一个 SSE 事件可能被拆到两个 chunk 里，或者多个事件合并在一个 chunk 里。你需要自己维护一个缓冲区，按 \n\n 分割事件。

如果你 hook 的是更底层的 API（比如通过 CDP 的 Network.getResponseBody），你拿到的是完整 body，没有流式顺序问题，但你就失去了实时性——必须等响应结束。

实际影响：按 \n\n 分割 + 缓冲区是标准做法，不难。真正的问题是如果站点用的是 WebSocket 而不是 SSE/fetch 流，你的 fetch hook 完全看不到。

5. chrome.debugger 拿响应体的替代方案

chrome.debugger 确实可以读响应体。CDP 的 Network.getResponseBody 或 Network.getResponseBodyForInterception 可以拿到完整响应，包括流式响应的最终拼接结果。

代价：

页面顶部会出现“正在调试此浏览器”的横幅，每次 attach 都出现-
。

一次只能 attach 一个 tab。

如果站点检测 CDP 连接（下面会说），attach 本身就会触发检测。

对流式响应，你拿到的是完整 body，不是实时的，除非你用 Network.dataReceived 事件自己拼接。

6. 站点检测扩展环境或 CDP 的方式

站点检测自动化/扩展的常见手段，按侵入性从低到高：

检测扩展痕迹：

chrome.runtime 是否存在：页面世界可以检查 window.chrome && chrome.runtime。但很多正常 Chrome 页面也有 chrome.runtime（来自其他扩展），所以这个信号很弱-
25
。

Error.stack 中是否含 chrome-extension:// 路径：如果你的注入代码抛错，堆栈会暴露扩展来源-
。

document.currentScript 的 src 属性：如果检测到 chrome-extension:// 开头的 src，说明有扩展注入。

检测 CDP：

console 序列化 getter 副作用：这是最隐蔽也最可靠的 CDP 检测。定义一个 Error 对象，在 stack 属性上挂 getter，然后 console.debug(err)。当 DevTools/CDP 连接时，console 序列化会触发 getter；没有 CDP 时不触发-
25
。

toString() 完整性：检查关键原生函数是否被包装。被 hook 的 fetch 的 toString() 不返回 [native code]-
。

Runtime.evaluate 时序：在页面中注入一个微任务，测量 performance.now() 的异常延迟，CDP 的 evaluate 会留下时序痕迹。

实际影响：如果目标站点是消费级 AI 对话产品，它做 CDP 检测的概率中等。做扩展检测的概率较低，但不是零。你的 hook 一旦被发现，站点可能静默降级——返回正常响应但混入水印或错误数据，而不是直接拒绝服务。

二、比 hook fetch 更稳的拿答案办法

逐个评。

读 IndexedDB 或内存中的会话状态

最稳，但覆盖面最窄。

如果站点把会话消息持久化在 IndexedDB 里，你可以直接读。IndexedDB 是页面世界和扩展世界都能访问的（共享 DOM/存储，但有隔离世界的限制——content script 在 isolated world 里可以访问 IndexedDB，但需要知道数据库名和对象存储结构）。

优点：

不 hook 任何原生函数，不被 toString() 检测。

不受流式响应分块问题影响——你读到的是最终持久化的完整消息。

站点改版通常不会改 IndexedDB schema（那是破坏性变更）。

缺点：

你必须先知道 schema。这需要一次性的逆向工程。

流式生成过程中，消息可能还没持久化——你要等生成结束才能读到。

如果站点用内存状态而不是 IndexedDB，这招无效。

不同站点的 schema 完全不同，不可移植。

适用性：如果你的目标站点确实用 IndexedDB 存会话，这是最优雅的方案。值得先花时间确认。

MutationObserver 监听消息容器 + DOM 结构判断结束

最“传统”，但最容易被改版打断。

监听消息容器的 DOM 变化，根据消息元素的结构变化判断“生成结束”（比如出现“停止生成”按钮消失、或出现复制按钮）。

优点：

不需要 hook 任何 JS API。

对 SSE/fetch/WebSocket 都有效——不管数据怎么来的，最终都渲染到 DOM。

缺点：

DOM 结构是站点改版最频繁改的东西。选择器、class 名、元素层级，任何一次前端重构都可能打断你。

流式生成时 DOM 会高频变化，MutationObserver 回调可能触发数千次，性能开销需要控制。

判断“生成结束”需要观察多个信号（按钮状态、元素属性、文本长度稳定），逻辑复杂。

如果站点用虚拟滚动或懒渲染，消息容器可能不在 DOM 里。

适用性：作为兜底方案可以，作为主方案不推荐。

performance.getEntries 或资源计时判断请求结束

几乎不可行。

performance.getEntries() 可以拿到资源加载的计时信息，但对 fetch/XHR 的流式响应，它只记录请求开始和结束时间，不给你响应内容。而且 fetch 默认不产生 resource timing 条目，除非设置了 Timing-Allow-Origin 或者用了 PerformanceObserver 监听 resource 类型。

实际影响：这招只能告诉你“有一个请求发生了”，不能告诉你“响应内容是什么”。对你拿到答案的目标没有帮助。

chrome.debugger 直接读网络响应

可行，但有侵入性代价。

前面已经说了：能读完整响应体，但会出现调试横幅，一次一个 tab，且 attach 行为本身可能触发 CDP 检测。

优点：

不依赖页面 DOM 结构，站点改版不影响。

拿到的是完整响应体，不需要处理流式分块。

可以读 WebSocket 帧（通过 Network.webSocketFrameReceived）。

缺点：

调试横幅对用户可见，体验差。

一次只能 attach 一个 tab。

如果站点检测 CDP，attach 会被发现。

需要处理 CDP 的事件流，复杂度高于 hook fetch。

适用性：如果你能接受调试横幅，且站点不检测 CDP，这是比 hook fetch 更稳的拿响应体方案。

注入脚本改包 EventSource 或 XMLHttpRequest

和 hook fetch 同等级，取决于站点用什么。

如果站点用 EventSource（SSE），你需要 hook EventSource 的 onmessage 或 addEventListener('message')。EventSource 的 hook 比 fetch 简单，因为 SSE 本身就是按事件分帧的，你不需要处理分块边界问题。但是 EventSource 的 message 事件只给你 data 字段，如果站点用自定义事件类型（event: xxx），你需要监听所有类型。

XMLHttpRequest 的 hook 更麻烦：你需要在 readystatechange 或 progress 事件里从 xhr.responseText 里截取增量。XHR 的 responseText 在 readyState=3 时是累积的，不是增量的——你每次拿到的是从开始到当前的全部文本，需要自己算差值。

实际影响：EventSource hook 比 fetch hook 更干净，但前提是站点用 EventSource。很多 AI 对话产品用 fetch + ReadableStream，不用 EventSource。你需要先确认目标站点的实现。

小结
方案	抗改版	实现复杂度	检测风险	实时性
IndexedDB	高	中	低	低（等持久化）
MutationObserver	低	中	低	高
performance API	—	—	—	—
chrome.debugger	高	高	中（CDP检测）	低（需自己拼）
EventSource/XHR hook	中	中	中	高

如果站点用 IndexedDB 存会话，优先读 IndexedDB。否则，chrome.debugger 和 fetch hook 各有代价，取决于站点是否检测 CDP。

三、扩展路线 vs 官方 API 路线

前提：个人账号，不想额外按量付费，偶尔人工登录可以接受。

维护成本

扩展路线：高。你要维护 content script、MAIN world 注入、Native Messaging host、命令行端。站点每次改版都可能打断你。MV3 的 service worker 生命周期、注入时机、权限模型都在持续变化。这是一个持续投入的项目。

官方 API：低。OpenAI 的 Responses API 提供内置的 web_search 工具，不需要你自己实现联网搜索-
。Agents API 甚至提供了托管的浏览器环境，可以做 computer use 级别的操作-
。接口稳定，有版本管理。

能力覆盖

网页版独有的东西：

联网搜索：官方 API 有 web_search 工具，可以开启-
。这不是网页版独有的。

智能体/Agent：官方 API 有 tool_search、function calling、remote MCP servers-
。网页版的“智能体”功能本质上就是这些工具的前端封装。

特定网页版独有的功能：如果你的目标站点是某个特定 AI 产品，它的网页版可能有该产品独有的功能（比如特定的文件格式支持、特定的记忆机制、特定的 UI 交互）。这些在官方 API 里不一定有对等物。

关键问题：你真正需要的是“网页版独有的能力”，还是“用网页版账号省下 API 费用”？

如果是后者，扩展路线是在用维护成本换费用节省。对于偶尔使用，费用节省可能不值得。

被封或失效时的恢复代价

扩展路线：站点改版 → 你的 hook 失效 → 你需要重新逆向 DOM/网络协议 → 恢复时间以小时到天计。如果站点检测到你的 hook 并封账号，你失去的是登录凭据，恢复代价更高。

官方 API：接口变更 → 官方有迁移指南和过渡期 → 恢复时间以分钟到小时计。API key 被吊销的概率极低（除非你滥用）。

结论

如果你的目标站点是 OpenAI 或其他有成熟官方 API 的产品，官方 API 路线的总成本几乎肯定更低，即使它按量付费。你的“个人账号、不想额外付费”前提，意味着你在用维护时间换取 API 费用——对于偶尔使用，这个交换不划算。

扩展路线只在一种情况下更划算：你需要的功能确实只有网页版有，官方 API 没有对等物，且你愿意接受持续的维护投入。

四、你问偏了的地方

你问的是“怎么 hook fetch 才能稳定拿到答案”，但更关键的问题是：

你 hook 到的响应体，和用户最终看到的答案，可能不是同一个东西。

网页版 AI 对话的响应流通常包含：

多个中间事件（thinking、tool_call、citation、delta）

最终拼接的文本

可能的后处理（水印、格式化、引用编号）

你 hook fetch 拿到的是原始字节流，你需要自己解析事件流、拼接 delta、处理引用编号。这些逻辑站点前端已经做了一遍，你在重新实现。如果站点改版，不仅 hook 点可能变，事件流的格式也可能变。

更该问的问题是：目标站点是否把“最终答案”暴露在一个更稳定的接口上——比如 IndexedDB 里的持久化消息、或某个内部 API 端点，返回的是已经拼接好的完整文本？

如果你的目标是“稳定拿到完整答案”，而不是“必须实时流式拿到”，读持久化存储比 hook 网络层更稳、更简单。
