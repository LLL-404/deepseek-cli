# Phase 1 需求梳理：DeepSeek命令行 全面换装 TypeScript

写于 2026-10-06。前提：用户解除「不引入第三方库」约束，并决定全面换装 TS。
四个关键分叉已于 2026-10-06 经用户逐项确认：**驱动路线=Playwright、旧版角色=保留为后备、扩展路线=搁置且文档保留、功能范围=全量对齐**。后续阶段如需推翻，回退到本阶段重议。

## 1. 核心目标（一句话）

把 DeepSeek 网页版命令行工具（现 Python 手写 Marionette 的 `dsk`）整体迁移到 TypeScript + 第三方库生态（主推 Playwright），能力等价或更强，项目硬规则不变。

## 2. 目标用户 / 场景

- 用户就是作者本人：单人、Windows、本地 CLI，无部署、无多用户。
- 场景不变：终端里 `dsk "问题"` → 浏览器代答 → stdout 出答案进管道/脚本；附带会话打标（`qoder｜` 前缀）与清理。
- 新场景（TS 路线解锁，P2）：答案边生成边打印到终端；答案以结构化形式（正文/思考/结束原因）输出。

## 3. 核心功能清单

### P0（问答链路，必须先立起来）

1. **环境建立**：Playwright persistent context（持久 profile 目录，登录一次长期用）替代「每次复制 profile」；登录态校验；崩溃残留清扫；`down` 一键整体删除（含登录态）。
2. **提问链路**：导航 → 两个开关（深度思考/智能搜索，默认全开）→ 填题 → 提交前验前提（无停止按钮）→ 等待判定 → 取答案 → 新会话改名打前缀。
3. **等待判定**：以 Playwright auto-wait 为主，`--max-wait` 总上限保留；完成判定沿用双信号思路（文本稳定 **且** 停止按钮消失），读数抖动容忍策略随库的稳定性重新评估（可能可以简化）。
4. **CLI 兼容**：现有参数面全保留（`--chat`、`--out`、`--mark`、`--file`、`--max-wait`、`up/down/status/chats/rm`、`--any`）；stdout 只有答案、stderr 只有过程；退出码契约明确为三档（0 成功 / 1 运行错误 / 2 前提不满足）。
5. **一锤子验证（风险闸门，开工第一件事）**：DeepSeek 对 Playwright 定制版 Firefox 的风控验证——能登录、能正常问答、没有验证码墙才算过；不过则整个 Playwright 路线退回备选（Selenium + 原版 Firefox）。

### P1（会话管理）

6. `chats`：列出会话。
7. `--chat 关键词`：命中 0 条或多条都拒绝并列出候选。
8. `rename` 打 `qoder｜` 前缀；`rm` 只认前缀会话（`--any` 越过）——白名单硬规则原样迁移。

### P2（补齐与升级）

9. 附件上传（`--file`，扩展名白名单）。
10. 离线测试：等待判定逻辑注入假读数（对齐现有 14 项测试思路）；不再有自写协议层，替代为对 mock 页面的 Playwright 测试。
11. 流式终端输出（边生成边打印）——依赖增量流可读；拿不到就维持整段返回。
12. `probe` 诊断工具 TS 化。

## 4. 边界约束

### 硬规则（不变，任何阶段不可违反）

- 不伪造 `bf`、`dltk` 这类反爬令牌；不在浏览器之外重放会话凭据。驱动真浏览器、由页面自己签名，这条天然满足。
- 删除只认 `qoder｜` 前缀会话，`--any` 才能越过。
- 不往外发正文和未公开设定；报错只带工具用法、错误原文、通用技术信息。
- 凭据所在的 profile 目录必须可一键删除（`down`），删后登录态消失；不再有「跑完必删副本」的义务（持久 profile 是常驻的，改为显式管理）。

### 技术栈决定（本阶段拍板，可推翻）

- 语言：TypeScript 全量；Node ≥ 24（原生跑可擦除语法的 .ts，CLI 入口不需要构建步骤）。
- 浏览器驱动：**Playwright（Firefox，persistent context）**；备选 Selenium + 原版 Firefox（保住 profile 副本模型）。
- 构建/测试工具链：允许引入，倾向最小集——`tsc --noEmit`（类型检查）、`esbuild`（仅在需要单文件入口时）、`node:test` 或 `vitest`。不引 Web 框架、不引 UI 库。
- 扩展路线（dsk2）：**搁置、文档保留**——若 Playwright 能拿到响应流，扩展路线的存在理由基本消失；DESIGN-dsk2.md 归档不删，风控验证失败时再启用。
- 旧 Python 版：**保留为后备**，TS 版过一周真实使用、没有出现「答案残缺但退出码 0」再退役（沿用 DESIGN-dsk2 阶段 5 判据）。

### 不做什么

- 不做 GUI、不做守护进程/后台常驻服务。
- 不追求跨平台（Windows 优先，path/进程相关代码允许 win32 特化）。
- 不做账号多开/并发实例（维持单实例语义，两终端同时跑仍需排队或明确报错）。
- 迁移期不改 Python 版功能（只修致命 bug）。

## 5. 最大的三个风险（作为 Phase 3 的输入）

1. **风控**：Playwright 的 Firefox 是定制构建，DeepSeek 登录/问答可能触发风控。P0 第 5 条的一锤子验证就是为此设的，是全计划的闸门。
2. **响应流可达性**：Firefox 上 Playwright 拿流式响应体的能力有已知限制（完成后全量 body 稳定，逐块增量不保证）；影响 P2 的流式输出，不影响 P0。
3. **登录态迁移**：现模型靠复制主 profile 继承登录态；Playwright 持久 profile 默认需要手动登录一次。「从主 profile 受控导入 cookie」作为备选方案在 Phase 3 论证。
