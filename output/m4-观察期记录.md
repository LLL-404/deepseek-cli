## 事故与缺陷记录（M4 首日，3 起全部修复）

### 事故 1：textarea click 被浮层卡死 → 机驱批次 12 连败

- 现象：12 问全部 exit=1、0 字；`locator.click: Timeout 30000ms`（hit-target 检查过不去）。
- 根因一（设计缺陷）：`fillAndVerify` 的 `ta.click()` 是 Marionette 时代 Cargo——Playwright `fill()` 自带 focus，click 的 hit-target 检查会被任何浮层卡死。旧 keeper 会话残留用户手动登录后的页面状态触发卡死；新会话复现不出（diag：topIsTextarea=true、零浮层）。
- 根因二（运维坑）：修复后首次冒烟仍败——**keeper 没重启，跑的还是旧逻辑**（常驻进程的「忘了重编译」孪生坑）。
- 修复：删除 click；追加运维纪律「改 keeper 侧代码必须重启 keeper」（版本握手留待后续）。
- 12 次失败全部响亮报错退 1，无一次假成功。

### 事故 2：F-3 无渲染黑洞再现 + busy 窗口

- 复现：冒烟#2 与冒烟#1 同题连续发送 → 提交被接受（输入框清空）但两轮（含刷新重取）全 noRender，keeper 忙约 8 分钟；工具响亮报错退 1。
- 运维误：机驱批次未确认 keeper 空闲就发问，12 问撞上忙窗口被拒（busy 退 2）——批次调度问题，非工具缺陷。
- F-3 当日累计 2 起（Q7 三连 + 本次），黑洞率 ≈ 2/80 提交。留观：唯一题复发则升级网络层观测。

### 事故 3：rm 菜单项点击被 hit-target 间歇卡死（已修复）

- 现象：演练在 M2 成功过、复跑即 click 超时（DELETE 菜单项可见可用但 hit-target 过不去）——菜单遮罩/React 重渲染间歇性挡指针。
- 修复：rm 与 rename 的全部菜单项点击改 **JS 合成点击**（`document.evaluate` 首匹配 + `el.click()`，与菜单打开同款；本站 React 委托对其响应可靠）。修复后三项演练取证干净。
- 取证教训：`node … | tail` 会让 `$?` 变成 tail 的退出码——首轮「演练全 0」是假证据，重跑以无管道方式重取。
- 文件编码教训：中文内容经 bash heredoc 追加落成 ANSI → 混合编码文件，Edit/Read 拒读；中文文件内容一律走 Write/Edit 工具。

## 归属标记改造（2026-10-06 追加）

需求：会话列表里分不清哪条是哪个 Agent 开的——前缀是硬编码常量 `qoder｜`，无论谁调用都落同一个。

### 改了什么

| 项 | 前 | 后 |
|---|---|---|
| 前缀来源 | `constants.ts` 硬编码 `MARK = "qoder｜"` | `src/agent.ts` 运行时决定：`--mark` > `DSK_AGENT` > 环境变量自动识别 > `unknown` |
| 识别位置 | —— | **CLI 侧**（keeper 是常驻进程，其环境属于第一个拉起它的 Agent，读不到后来的调用方） |
| 默认会话 | 全局唯一 `qoder｜连续会话` | 每 Agent 一条 `<Agent 名>｜连续会话`，互不共用 |
| 蹭会话 | 找不到就复用任意自有会话 | 只复用本 Agent 的；跨 Agent 要 `--chat` 显式指定 |
| rm 白名单 | 硬编码 `[qoder｜, dsk｜]` | 动态：全部已知 Agent 前缀 + 历史遗留 + 本次 mark |
| 会话列表 | `[dsk]` 标记 | 每条标出归属前缀，本 Agent 行首 `*`，`—` = 无前缀 |
| 新增命令 | —— | `dskts whoami`（这次被认成谁、凭什么） |

识别表两级：**强特征**（应用注入的进程级变量）先扫一轮，**弱特征**（`*_HOME` 这类可能被用户手工持久设置的）才轮到。

三条实测教训写进了代码注释与 README：
1. 本机 `DSH_HOME` 是用户级持久变量，任何 Agent 的子进程都能看到——不分两级就会在 Cursor 里被抢认成 DeepSeek Harness。
2. WorkBuddy 必须排在 Claude Code 之前：CodeBuddy/WorkBuddy 一并注入 `CLAUDE_SESSION_ID`、`CLAUDE_CODE_GIT_BASH_PATH`；Claude 规则因此只认 `CLAUDECODE` / `CLAUDE_CODE_ENTRYPOINT`。
3. 识别不能在 keeper 里做（理由见上表）。

### 顺带修掉两处改名缺陷（都是既有 bug，非本次引入）

改名一直只写日志不生效，本次顺藤摸到两处，都在 `pageops.ts`：

| # | 症状 | 根因 | 修复 |
|---|---|---|---|
| 1 | `Document.evaluate: Result type mismatch` | `renameTo` 把 Playwright 语法串 `"xpath=//div[...]"` 整串喂给 `document.evaluate`；XPath 被解析成 `xpath = //div[...]` 比较表达式，返回布尔值，与请求的 `FIRST_ORDERED_NODE_TYPE` 类型不符 | `clickXpathFirst` 剥掉 `xpath=` 前缀；调用处改用裸 XPath，与 rm 统一 |
| 2 | `An attempt was made to use an object that is not, or is no longer, usable` | 手搓 `evaluate` 里取 `window.HTMLInputElement.prototype` 的 native setter 设值，元素被 React 重渲染换掉后成为死对象 | 改用 Playwright 原生 `locator.fill()` + `press("Enter")`——与已验证可行的 `fillAndVerify` 同一条路径 |

修后实机：`已改名：? → WorkBuddy｜连续会话`。README 里「改名仍落 `qoder｜连续会话`」的差异条目已作废。
